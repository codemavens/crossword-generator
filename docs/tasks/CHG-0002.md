# Phase 1: application foundation

## Intent

Stand up the running local application described in `../SPEC.md` §21 Phase 1: a React/TypeScript/Vite frontend, a local Node.js service with SQLite project persistence, shared TypeScript models, a basic form for a family name and list of names, and a simple manually constructed crossword grid rendered as SVG.

## Background

The V1 specification was committed under CHG-0001 and reviewed on 2026-11-13. The user is ready to begin development. Phase 1 is the first of nine phases and everything later builds on its structure.

Decisions made by the user during the review on 2026-11-13:

- Keep SQLite, using Node's built-in `node:sqlite`.
- Do not run the app in Docker, and do not change machine-level nvm or npm config. Run on the system Node (24.11.1 at the time of writing) and record the requirement in the project.
- Test runner: Node's built-in `node:test`.
- Approved packages: `react`, `react-dom`, `vite`, `@vitejs/plugin-react`, `typescript`, `@types/react`, `@types/react-dom`, `@types/node`.
- Branching: `develop` created from `main`; work on `feature/app-foundation`.
- One Node process serves both the API and the built frontend. Paper.js is deferred until a phase needs it.

**Status: Approved by the user on 2026-11-13** with the recommendations above.

Linear tickets: None identified.

## Acceptance criteria

- AC1: `.nvmrc` and `package.json` `engines` record the Node requirement (24, minimum 24.11.0), and the service exits with a clear message when started on an older version.
- AC2: One documented command starts the app for development, and the page loads in a browser.
- AC3: The page has inputs for project name, optional customer name, family name, optional year and a list of names. Names shorter than two characters are rejected with a visible message.
- AC4: A project can be created, saved, listed, reopened and deleted through the local API, and it survives a restart of the service.
- AC5: The SQLite table matches `../SPEC.md` §14.2, the design is stored as one JSON document with a schema version, and all database access goes through an application-owned repository interface.
- AC6: The shared models from `../SPEC.md` §15 exist as TypeScript types used by both frontend and service.
- AC7: A hard-coded sample arrangement renders as an SVG grid of uniform square tiles with letters, sized from the tile-size setting in millimetres.
- AC8: Automated tests cover the repository (create, read, update, delete, list) and name-length validation, and pass from one documented command.
- AC9: Dependencies are pinned to exact versions, the lockfile is committed, and `docs/DEPENDENCIES.md` lists each package with version, licence and purpose.
- AC10: `README.md` documents setup, run and test commands. The database file and build output are ignored by Git.

## Constraints / Architecture direction

- Perform implementation and validation in a dedicated task worktree. Preserve the user's original checkout and all existing local changes.
- Follow `../SPEC.md`. Phase 1 adds no solver, connector, frame-geometry or export logic.
- Engine code (models now; solver, geometry, typography, export later) lives where it cannot import React, the DOM or the database.
- Install no dependency that is not approved. `opentype.js`, `clipper2-ts` and Paper.js are approved but are not installed until a phase uses them.
- The service uses `node:http` and `node:sqlite`, and runs TypeScript directly on Node without a separate runner.
- The service listens on localhost only.
- Keep code comments brief.

## Security considerations

Proposed during drafting; to be confirmed by the user.

- The API binds to `127.0.0.1` only and has no authentication, on the basis that it is a single-user local tool.
- All SQL uses prepared statements. Request bodies are validated and size-limited before being stored.
- The database file holds customer names. It stays out of Git and out of logs.
- No SVG upload or file-system export is added in this phase, so SVG sanitisation is not yet in play.

## Out of scope

- Crossword solver, scoring and candidate generation (Phase 2).
- Connectors, decorative tiles and artwork (Phase 3).
- Tile union, score lines, frame, backer and SVG export (Phases 4, 5 and 7).
- Project search, duplicate and JSON import/export (Phase 8).
- Amending `../SPEC.md` for the gaps found in the review.

## Open questions

- Whether a newer Node 24 release removes the `node:sqlite` experimental warning is unverified. The warning is harmless.
- The Security considerations above were proposed during drafting and approved as part of the brief without separate discussion.
- The specification gaps found in the review (connector geometry, enclosed holes, frame algorithm, reference image) are unresolved and block Phases 2, 3 and 5, not this task.

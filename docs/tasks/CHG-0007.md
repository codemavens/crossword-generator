# Tile artwork: built-in pictures, uploaded SVG and per-tile choice

## Intent

Let each decorative tile carry its own picture: one of a small built-in set, an SVG the user uploads, or nothing. This completes Phase 3 in `../SPEC.md` §21.

## Background

Connectors and manual end tiles exist (CHG-0006, PR #5), but every tile is blank in the saved data and the app draws the same placeholder heart on all of them. `../SPEC.md` §5.4 requires each tile to be individually configurable, and §17.5 requires uploaded SVG to be validated and made safe. Artwork was split out of CHG-0006 with the user's agreement because uploaded files need their own safety work.

Linear tickets: None.

**Status: Draft, awaiting the user's approval.**

## Acceptance criteria

- AC1: The app ships a built-in set of pictures drawn for this project: heart, star, paw print, spade, cat face and cow.
- AC2: In "Edit end tiles" mode, clicking any decorative tile (automatic connector or manual tile) opens a small editor offering: each built-in picture, each picture already uploaded to this project, Upload SVG, Blank, and, for manual tiles only, Remove tile.
- AC3: Changing one tile's picture does not change any other tile, does not move anything and does not run the solver. The choice is saved with the project and shown again after reopening.
- AC4: A newly created automatic connector or manual tile starts with the filled heart. The user can change it to any picture or to blank.
- AC5: Generating again and picking a new arrangement starts its tiles at the default again, as `../SPEC.md` §6.5 allows. Uploaded pictures stay available in the project.
- AC6: An uploaded SVG is never stored or displayed as raw SVG. It is converted to plain shape outlines (paths plus a bounding box), and only that converted form is stored and drawn.
- AC7: The conversion keeps only basic vector shapes (path, rectangle, circle, ellipse, line, polyline, polygon, and groups with transforms). Scripts, event handlers, links, images, text, style sheets, foreign content, animation and any reference to an outside address are dropped. A file with nothing usable left is refused with a message.
- AC8: Uploads are limited to 200 KB per file, 20 uploaded pictures per project, and a fixed limit on shape data per picture. A file over a limit is refused with a message and nothing is stored.
- AC9: Each picture is drawn centred in its tile, keeps its proportions, and stays inside a margin of 15% of the tile size on every side, whatever the tile size.
- AC10: Pictures are drawn as engraving (solid fill, the engraving colour), never as cut lines. If an uploaded file contains only outlines with no filled shapes, the app warns that outlines alone will not engrave.
- AC11: The user can delete an uploaded picture from the project. Tiles using it become blank.
- AC12: Candidate thumbnails still show decorative tiles in a different colour; they do not need to show the picture.
- AC13: The server refuses a saved project whose artwork is not in the converted form, exceeds the limits, or contains anything other than shape data.
- AC14: A project saved before this change still opens; its tiles show the default heart.
- AC15: Automated tests cover the conversion (each dropped item in AC7, a transform, each limit in AC8), the scaling in AC9, AC11, AC13 and AC14.

## Constraints / Architecture direction

- Perform implementation and validation in a dedicated task worktree. Preserve the user's original checkout and all existing local changes.
- The saved form of a picture is application-owned plain data. The rule checks for it live in `src/core` so the server and the app share them. Reading the uploaded file uses the browser's own inert XML parser in `src/app`; nothing from the file is ever inserted into the page.
- Scaling and placement are pure functions in `src/core`, reused later by the exporter (Phase 7).
- Built-in pictures are original drawings stored in the repository in the same plain form as uploads. No icon library and no new dependencies.
- Artwork lives in the project (`project.artwork`), and a tile refers to it by `artworkId`. Layout rules, the solver and the validator are unchanged.
- The branch is stacked on `feature/connectors` (PR #5) until that is merged.
- Keep code comments brief.

## Security considerations

Proposed during drafting; to be confirmed by the user.

- An uploaded SVG is untrusted. It is parsed without being rendered or executed, reduced to an allow-list of shape data, and the original file is discarded (AC6, AC7).
- Shape data is checked again by the server on every save (AC13), so a hand-edited request cannot store markup.
- Size and count limits (AC8) keep a saved project inside the existing 2 MB request limit and keep drawing cheap.
- No new API routes, no network fetches for artwork, and no new dependencies.
- File names are used only as a display label, length-limited and shown as text.

## Out of scope

- Turning pictures into final engraving paths in exported files (Phase 7).
- Converting outlines (strokes) into engravable shapes, and colours or gradients in uploads.
- Raster images (PNG, JPEG) and text inside SVG.
- A shared picture library across projects.
- Rotating, resizing or repositioning a picture inside its tile.

## Open questions

- Default picture for new tiles. Proposed: the filled heart (AC4), as shown now.
- The built-in list. Proposed: the six in AC1, taken from the examples in `../SPEC.md` §5.4.
- Margin. Proposed: a fixed 15% of the tile size; a setting can be added later if needed.
- Outline-only uploads. Proposed: accept with a warning (AC10) and leave outline conversion for later.

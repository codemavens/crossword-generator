# Remaining V1 work: crossword cut geometry, design controls, export, project workflow and validation

## Intent

Finish V1 as defined in `../SPEC.md` §26: turn the chosen crossword into real cut, score and engrave geometry, let the user choose their own fonts and move and resize the design, export laser-ready SVG files for all three pieces, complete the day-to-day project workflow, and validate the result. This covers Phases 4, 6, 7, 8 and 9 in `../SPEC.md` §21.

## Background

Phases 1–3 and the frame are merged (PRs #1–#6). The app can generate, pick and decorate a crossword and preview it inside the real frame, but the crossword preview is drawn from tile squares, not from cut geometry, and nothing can be exported yet.

The user asked on 2026-11-14 for one brief covering every remaining step so the work can continue while they are away. The work is delivered in five stages, each as its own pull request, in the order below.

## Acceptance criteria

### Stage A — Crossword physical geometry (Phase 4)

- AC1: A geometry module in `src/core` turns a layout into Piece 1 in millimetres: the cut outline, the score lines, and the engraving outlines. Every tile is a square of exactly the configured tile size; changing the tile size rescales everything.
- AC2: The cut outline is the union of all occupied squares (letters, punctuation, decorative and blank tiles): one outer closed path, plus one closed path for each enclosed hole. A square shared by two names appears once.
- AC3: Each boundary between two occupied squares is scored exactly once. No score line lies on a cut line, and no cut or score segment is duplicated or overlaps another.
- AC4: Each letter or punctuation tile has its character engraved as a font outline, uppercase, centred in the tile. The tile font is chosen by id; the default is Zilla Slab SemiBold. A character the tile font cannot draw is a validation error that names the character.
- AC5: Point values are a single on/off setting, on by default. When on, each letter tile shows its standard English Scrabble value in the lower-right corner; an accented letter uses its base letter's value; punctuation and decorative tiles show none.
- AC6: Each decorative tile's picture is turned into engraving outlines using the placement rule from CHG-0007 (centred, proportions kept, 15% margin).
- AC7: The app preview draws the crossword from this geometry, with cut, score and engrave shown in distinct colours, so the preview and a later export cannot disagree.

### Stage B — Fonts, moving and resizing (Phase 6)

- AC8: The app has a font library. The user can add font files from their computer (TrueType and OpenType, and WOFF if the font library can read it), several at once. Added fonts are stored by the local service and are available to every project, so a design still reproduces when the original font folder is not connected.
- AC9: Each of the three font settings (family name, year, tile letters) is a picker listing the bundled fonts and the added fonts by name. Changing a font redraws the preview. A font can be removed from the library; a project that uses a missing font says so clearly, shows the default font in its place, and cannot be exported until a font is chosen.
- AC10: A font file that is not a readable font, or is over the size limit, is refused with a message and nothing is stored.
- AC11: The whole crossword can be dragged inside the frame with the mouse, and nudged with the arrow keys. The position is saved with the project. A "Centre" button puts it back in the default position. Fit is rechecked as it moves.
- AC12: The crossword can be resized easily: the tile size has a slider as well as a number field, and a "Largest that fits" button sets the biggest tile size at which the crossword fits the frame in its current position. The letter size inside a tile is a setting (a percentage of the tile size) so letters can be made bigger or smaller.
- AC13: The frame and backer can be resized easily: the diameter has a slider as well as a number field, and a "Smallest that fits" button sets the smallest diameter at which the crossword fits. The frame and backer always share one diameter.
- AC14: The buttons in AC12 and AC13 change a size only when the user presses them. Nothing else changes a manufacturing size.
- AC15: The app has the remaining controls from `../SPEC.md` §18.2: point values on or off, and the minimum gap between crossword and frame.
- AC16: The app shows sizing and fit feedback: tile size, frame diameter, the crossword's overall width and height in millimetres, whether it fits, and a suggestion when it does not.

### Stage C — Production export (Phase 7)

- AC17: The app exports three separate files: `crossword.svg`, `frame.svg` and `backer.svg`. Files are downloaded by the browser; nothing is written by the server.
- AC18: Every exported file states its physical size with `width` and `height` in millimetres and a matching `viewBox`, so 1 unit is 1 mm.
- AC19: Each file separates operations into named groups with distinct colours: cut red `#FF0000`, score blue `#0000FF`, engrave black `#000000`. The three colours are project settings the user can change.
- AC20: Cut and score paths are strokes with no fill; engraving is filled outlines with no stroke. All text is outlines; no file contains a `<text>` element, a font reference, a script, an image or an outside address.
- AC21: In `crossword.svg`, hole cuts come before the outer cut. In `frame.svg`, the outer edge is a true circle and the inner cut is a single path; the name and year are engraving. `backer.svg` is one circle matching the frame's outer edge.
- AC22: Export is not offered when the crossword has structural errors, no arrangement is chosen, or a font is missing. When the crossword does not fit the frame, export requires an explicit confirmation.
- AC23: Automated tests check AC18–AC21 on generated files, and that the exported geometry equals the preview geometry. If Inkscape's command line is available on this machine, a scripted check confirms each exported file's size in millimetres; if it is not, that is reported instead.
- AC24: A short checklist for importing the files into LightBurn (sizes, three operations, cut order) is added under `docs/`, for the user to run. The result of that manual check is not claimed by this task.

### Stage D — Project workflow (Phase 8)

- AC25: The project list can be filtered by project name or customer name.
- AC26: A project can be duplicated; the copy has a new id and a name marked as a copy, and is independent of the original.
- AC27: A project can be exported as a JSON file and imported from one. An imported file goes through the same checks as a normal save, gets a new id, and is refused with a message if it is invalid or too large.
- AC28: A customer proof image of the assembled design (frame, backer, crossword, name and year, without the editing aids) can be downloaded as a PNG, 2000 pixels wide.
- AC29: Reopening a saved project reproduces the same design: same arrangement, position, tiles, pictures, fonts and settings.

### Stage E — Validation and handover (Phase 9, automated part)

- AC30: An automated end-to-end test follows `../SPEC.md` §26 steps 2–17 without a browser: create a project, generate, choose, add a decorative tile, set a picture, export the three files, save, reopen, and export again with identical output.
- AC31: Every geometry and export test listed in `../SPEC.md` §20 has an automated test, or is listed in the handover note as needing a person (LightBurn import, Inkscape inspection, laser cutting).
- AC32: A README explains how to install, run and use the tool, and a physical-test checklist lists what to cut and what to measure so the defaults (tile size, diameter, ring width, fonts, colours) can be tuned.
- AC33: `../DEPENDENCIES.md` and `../SPEC.md` are brought up to date with what was built, with dated amendments for any behaviour that differs from the spec text.

### Every stage

- AC34: All tests pass, the typecheck is clean and the build succeeds before a pull request is opened; the stage is checked in a browser where it has a user interface; Codex reviews the branch and its critical and high findings are fixed.

## Constraints / Architecture direction

- Perform implementation and validation in a dedicated task worktree. Preserve the user's original checkout and all existing local changes.
- One pull request per stage into `develop`, in order A to E. If an earlier stage is not merged yet, the next branch is built on top of it and its pull request says so; they are to be merged in order.
- Geometry stays in `src/core`, free of React, DOM and Node, in millimetres. The exporter is a pure function from geometry to SVG text and lives in `src/core`, so the preview, the tests and the download all use the same code.
- The crossword outline is computed exactly from grid edges, not approximated. `clipper2-ts` stays behind the existing polygon module and `opentype.js` behind the typography module. No new dependencies unless a stage cannot be done without one, in which case work stops for approval.
- Added fonts are stored in the existing SQLite database by the local service and served only to the local app. The font picker reads one list that merges bundled and added fonts. Font files are never added to the repository.
- Geometry is never stored. Only project data is saved, and files are regenerated from it (`../SPEC.md` §14.3).
- Manufacturing sizes change only on an explicit user action (AC14).
- Dragging changes only the layout's offset in millimetres; grid positions and the solver are untouched.
- Keep code comments brief.

## Security considerations

Proposed during drafting; the user approved the section on 2026-11-14. The font-library points below were added with the amendments and follow the same approach.

- An imported project file is untrusted. It is size-limited, parsed as JSON only, and passed through the same validation as any save, including the artwork checks from CHG-0007. It can never overwrite an existing project because it always gets a new id.
- An added font file is untrusted. The local service accepts it only from the local app (same Host and Origin checks as every other route), limits its size, checks that it parses as a font before storing it, and stores it under an id it generates, never under a path or name from the file. Fonts are served back only as binary data to be parsed, never as a page.
- The font routes read and write the database only. They never read from or write to a path supplied in a request, so the service cannot be used to read other files on the computer.
- Font names shown in the picker come from the font file and are treated as plain text, length-limited.
- Exported SVG is built only from application geometry. Names, project names and file names from the user never enter a file as markup; download file names are reduced to safe characters.
- Exported files contain no scripts, links, images or outside references, so they are safe to open in other tools. Exported files contain letter outlines only, not the font itself.
- Export, import and the proof image run in the browser. No calls to outside services. The optional Inkscape check is a developer script, not part of the running app.
- No new secrets or personal data beyond the customer name already stored locally.

## Out of scope

- Physical laser tests, the LightBurn import itself and final tuning of defaults: these need the user and the machine. Checklists are provided.
- A combined cutting sheet. The user wants three separate files.
- Reading fonts directly from a folder on disk. Fonts are added through the picker instead (see Open questions).
- Autosave. `../SPEC.md` lists it as optional; explicit Save is kept.
- Dragging or editing individual names or tiles (`../SPEC.md` §10.2). Only the whole crossword moves.
- Showing sizes in inches. Millimetres only for now.
- Outline-only (stroke) artwork conversion, raster images, a shared picture library.
- Blender previews and any of the later features in `../SPEC.md` §22 other than whole-crossword dragging.
- Kerf compensation and structural reinforcement of thin joins.
